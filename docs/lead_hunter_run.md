# Lead Hunter: самостоятельный запуск, этапы 1–2

Запуск из корня проекта, без Codex и без входного JSON:

```sh
.venv/bin/python -m app.lead_hunter run --city Шымкент --limit 3
```

`--direction new-crm` и `--direction existing-bitrix24` выбирают потоки поиска;
по умолчанию работают оба. Поисковый поток — направление исследования, а не
доказательство наличия или отсутствия CRM. Итоговую категорию определяет v1.2
после проверки видимых записей Битрикс24. У подтверждённого клиента сохраняется C,
даже если предложение удерживается из-за неполной истории. Лимит этапа — три
проверенные компании, без пополнения архивными данными.

Дополнительные разрешённые источники можно настроить через `--sources SOURCES.toml`.
Это реестр адресов, а не готовые результаты исследования. Содержимое реестра
фиксируется при запуске. Типы: `rss` (RSS/Atom этого издателя), `index` (индекс
публикаций с узким `path_prefix`), `employer` (официальная страница работодателя,
поле `employer`). Например, для разрешённого пресс-раздела:

```toml
[[sources]]
name = "kazakh-invest"
kind = "index"
url = "https://invest.gov.kz/ru/media-center/press-releases/"
path_prefix = "/ru/media-center/press-releases/"
```

Адреса регистрируйте только после проверки правил источника. Механизм не читает
закрытые страницы, не следует переадресациям и не использует HH API для продаж.
Бесплатный поиск ограничен покрытием подключённых источников. Есть отдельные
запросы по внедрению и по действующему Битрикс24; исходные HTML/RSS не считаются
доказательством до проверки конкретного факта. Текущая проверка текстов опирается
на ограниченный словарь, преимущественно русскоязычный. Отдельный сбор из
рекламных кабинетов, соцсетей и закрытых досок вакансий не подключён.

Для проверки публичного поиска без CRM добавьте `--public-only`. При необходимости
задайте новый `--run-dir`. Для продолжения используйте каталог, который команда
напечатала при запуске:

```sh
.venv/bin/python -m app.lead_hunter run --resume outputs/lead_hunter/runs/ID
```

У запуска зафиксированы город, лимит и режим. Повторно используются найденные
URL, завершённая проверка каждого URL, полный доступный снимок совпадений и
завершённое чтение истории каждой компании. Прерванная единица может повториться.
Полный индекс CRM не сохраняется; если прервано чтение индекса, сканирование
повторяется. Неполное чтение CRM и отказ всех поисковых источников не считаются
успешными контрольными точками. Подтверждённые прошлым запуском даты не
переписываются. Для нового чтения источников начните новый запуск.

В приватном каталоге лежат `events.jsonl`, снимки проверок, `evidence.json`,
`summary.json`, `report.xlsx`, `report.md` и `review.csv`. Журнал этапов показывает
завершение, повторное использование, ошибки и число попыток CRM; URL и причины
пропусков находятся в контрольных точках поиска и проверки. В журнал не попадают
вебхук, ключи, сырые ошибки HTTP, запросы к модели и тексты CRM. Excel содержит
сводную, четыре категории и лист «Квалифицировать». Свежий предметный сигнал
может попасть в эту очередь даже с низким NEED; контакты по ней не разрешены.
Лист HOLD может пересекаться с категориями: удержание предложения не меняет
тип отношений. `found_sources` — найденные результаты поиска, `researched` —
уникальные проверенные компании; `excluded` — явный запрет обращения,
`needs_review` — остальные без активной рекомендации. Эти показатели не означают
покупательский интерес.

`awaiting_llm` означает, что поиск и проверка прошли, а AI-этап ещё не подключён.
`public_only` означает, что CRM пропущена по флагу. `partial_public`, `partial_crm` и
`discovery_unavailable` возвращают код 2 с отчётом. `stale_crm_snapshot` тоже
возвращает код 2: возобновление не перечитывает проверенную CRM, для актуализации
нужен новый запуск. `no_verified_candidates`
означает, что после поиска не осталось подтверждённых строк. При прерывании
верифицированные контрольные точки сохраняются. Эти статусы не означают
сформированные персональные предложения или разрешение на контакт.

Универсальный экспорт существующего v1.2 JSON, без сети:

```sh
.venv/bin/python -m app.lead_hunter export-xlsx EVIDENCE.json --output REPORT.xlsx
```

Без `--as-of` решение считается на текущую дату на основании исходных отметок.
С `--as-of '2026-11-05T17:51:20+05:00'` результат — явно исторический;
он не даёт текущего допуска. Старые сценарии сборки под `outputs/` были записаны
для конкретных отчётов и не являются механизмом обновления источников.

На листах нового внедрения и доработки Битрикс24 рядом с компанией видны
WhatsApp, тема и текст email, один призыв к действию и рекомендуемый канал.
Внутренняя гипотеза, продукт и её источники хранятся отдельно от текстов.
Экспорт читает проверенный `commercial_proposal.outreach_copy` из пакета.
Пустой черновик помечается явно. Категории C и D, архивные снимки и записи без
допуска не публикуют холодные тексты.

Функция `draft_candidate` в `app.services.lead_hunter_run` принимает явно
переданный runtime и формирует пару черновиков для проверенного предложения A/B.
Обычная команда `run` по-прежнему работает без провайдера и помечает этот этап
как `awaiting_llm`.

Перед этапом 3 нужен выбор работающей локальной модели или согласование внешнего
провайдера и бюджета. Текущая команда не читает OpenAI-ключ, не вызывает LLM и
не запускает отправителей. Закрытая история CRM не входит во внешний вход модели.
Подготовленный Responses-адаптер принимает отдельную схему только публичных фактов,
резервирует лимит до обращения к ключу и учитывает токены и расходы без текстов
запросов. Установка `OPENAI_API_KEY` сама по себе ничего не активирует.
После подключения модели менеджер проверяет её черновики; отметку человека
нельзя выставлять автоматически. Для SANBEL действуют регрессии v1.2: похожее
название не разрешает спорное совпадение, WON не доказывает исполнение, отказанное
предложение блокируется без нового основания.
