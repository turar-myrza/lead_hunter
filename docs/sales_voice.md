## Передача сценария в Robovoice

В опубликованном контракте Robovoice метод `POST /call/` принимает номер и ID кампании. Для индивидуального сценария предусмотрен `POST /scripts/invoke`. Его документированный объект принимает `scriptId`, `channel.type=2` для SIP, идентификатор SIP-аккаунта в `channel.id`, номер в `contact.account` и словарь `parameters` со строковыми значениями. Для статусов документированы `GET /call/state/{id}` и `GET /call/info/{id}`. `API-TOKEN` обязателен для работы с аккаунтом. [Robovoice Swagger](https://my.robovoice.ru/api/v1/docs/doc.json).

`prepare_robovoice_handoff(VoiceDossier(...))` собирает локальный предпросмотр структуры с названием, клиентским предложением и языком. В нём используются заполнители для номера, SIP-аккаунта и сценария. Входящие URL доказательств остаются в досье платформы. Публичный контракт подтверждает тип параметров, а имена переменных и их использование нужно сверить с конкретным сценарием.

После восстановления авторизации проверить настройки доступного сценария и SIP-линии по `GET /scripts/{id}/options` и `GET /settings/communications`. До проверки вызова разрешённого абонента установить, создаёт ли сценарий новые записи у провайдера и где обрабатываются реплики. Swagger предупреждает, что вызов по `contact.account` может создать контакт Robovoice. Параметр `recordCallFromDial=false` описан как начало записи при ответе абонента. Для проверки конфигурации без записи этот флаг сам по себе недостаточен. [Robovoice Swagger](https://my.robovoice.ru/api/v1/docs/doc.json).

## Проверки перед включением маршрута

- **Персональные данные.** Закон РК о персональных данных в статье 7 устанавливает сбор и обработку с согласия с предусмотренными законом исключениями. Публичная публикация номера сама по себе не подтверждает разрешение голосовой кампании. Для автоматического контакта храните датированное основание для данного получателя, цели и канала. Сценарий с общим телефоном юридического лица и сценарий с личным номером требуют проверки применимости. [Закон РК о персональных данных](https://old.adilet.zan.kz/rus/docs/Z1300000094/compare/eng) · [Закон РК о рекламе](https://law.gov.kz/api/documents/17905/rus/download/pdf).
- **SIP.** Закон РК № 320-VIII от 19.06.2026 изменил закон о связи. Для генерированных автоматических вызовов с предварительно записанными сообщениями предусмотрено специальное условие пропуска по договору с оператором. Закон определяет генерированные автоматические вызовы через количество соединений в минуту. Применимость к двустороннему AI-диалогу и правила действующего транка нужно подтвердить у оператора и юриста по выбранной кампании. [Поправки к закону о связи](https://adilet.zan.kz/rus/docs/Z2600000320).
- **WhatsApp.** Правила WhatsApp Business требуют полученный от человека opt-in на последующие сообщения или звонки и соблюдение запрета на повторное обращение. Провайдер WhatsApp Calling проверяет техническое разрешение на вызов отдельно. [Политика WhatsApp Business](https://whatsappbusiness.com/policy/) · [Документация WhatsApp Calling](https://developers.facebook.com/docs/whatsapp/cloud-api/calling/business-initiated-calls).
- **AI и запись.** Статьи 16 и 21 закона об AI предусматривают информирование об использовании AI и возможность отказаться от взаимодействия с системой, если оно не обязательно по закону. Голосовое начало содержит явное представление. Для синтетических результатов статья 21 отдельно предусматривает маркировку и предупреждение. Способ исполнения для выбранного аудиопотока уточните при правовой проверке. Для записи и транскрипции проверьте уведомление, основание обработки, хранение и передачу провайдеру. При запросе на включение записи требуется отдельная отметка проверки. [Закон РК об искусственном интеллекте](https://old.adilet.zan.kz/eng/docs/Z2500000230/compare) · [Гражданский кодекс РК, статья 144](https://www.gov.kz/org/adilet-bko/documents/details/475452?lang=ru).

Для проверки существующего маршрута нужны имя оператора, фрагмент договора об автоматических вызовах, идентификатор разрешённой исходящей линии, способ запуска вызова и получения событий, уровень доступа к просмотру статистики, утверждённый тестовый номер и сценарий перевода на менеджера. Параметры доступа остаются в настройках провайдера. Тест технического маршрута считается пройденным после двустороннего разговора, проверки переключения RU/KK, подтверждения статуса вызова и перевода. Клик по кнопке вызова или проигрывание текста подтверждает другой вид вызова.

## Как проверить работу локально

```python
from app.services.sales_voice import VoiceDossier, simulate_voice_dialogue

dossier = VoiceDossier(
    company='Учебная компания',
    offer='Покажем, как привязать запрос к заказу и назначить ответственного.',
    product='Доработка Битрикс24',
    language_variants={'kk': 'Сұрауды тапсырыспен байланыстырып, жауапты адамды тағайындау жолын көрсетеміз.'},
)
result = simulate_voice_dialogue(dossier, ['Қазақша айтыңыз', 'Бағасы қанша?', 'Иә'])
assert result.transport == 'simulated'
assert result.language == 'kk'
assert result.handoff
```

`VoiceDossier` хранит подготовленный текст предложения и язык. Симулятор поддерживает выбор языка на каждой реплике, ответ по разрешённому досье, передачу запроса менеджеру и завершение разговора при отказе. Событие передачи означает запрос на следующий шаг. Встреча фиксируется по отдельному подтверждённому результату.

`evaluate_call_admission` возвращает причины отказа при отсутствии действующей кампании, правовой и операторской проверок, разрешённого сегмента, соответствующего каналу согласия, лимита или тестового номера. Функция сама не вызывает сеть и не резервирует лимит. Боевой вызов должен брать утверждённые записи из доверенного хранилища и атомарно проверять остановку кампании и лимит перед передачей провайдеру.
